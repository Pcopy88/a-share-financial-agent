# 开发题集与公式准备说明

这批文件包含开发资料、财务参考和正式年报 50 题。代码已实现并进行本地验收；所有模拟记录标记 mock，真实云端模型质量仍待用户配置 Key 后验证。最新结果以 ../docs/验收文档.md 为准。

## 文件用途

- sample_manifest.json：登记实际 PDF、文件哈希、物理页数、文档类型、日期和已确认的轮次。
- development_inquiry_v1.jsonl：问询资料的开发题；一行一道题，保留问题、预期行为、答案要点和原文依据。
- financial_formula_reference.json：财务公式、使用条件、单位和来源；8 项公式的设计参考；对应 Decimal 实现在 src/annual_report_agent/finance/calculator.py。
- jiangfeng_2026h1_reference.json：江丰电子半年报的 18 条原文财务参考值和 5 道计算开发题，保存期间、合并口径及页码；不代表应用已自动抽取或通过评测。
- 开发题集与公式预览.md：便于直接阅读的问题、答案和公式。

## 一道题怎样使用

1. 先选定题目允许使用的文档和过滤条件。
2. 将问题和范围传给应用；不要把参考答案或标准证据直接传给待测模型。
3. 应用按正式流程进行改写、检索、计算、回答和引用校验。
4. 另外保存本次检索片段、逐项答案、引用页码、耗时、模型和配置版本，以及各云端调用的 usage、重试次数和费用估算。
5. 再与题集比较：资料是否选对、答案关键点是否齐全、数字和单位是否正确、引用是否支持结论、该澄清时是否澄清。

解释类答案不要求逐字相同。正面要点和禁止出现的错误说法分开检查；数字题根据单位和原文精度比较。评判可由程序与人工复核配合完成，不能只凭模型自报“正确”就算通过。

gold_evidence 中的页码和引文是已核对的参考证据，不保证已经穷尽所有可支持同一答案的页面。系统引用同一允许文件中的其他页面时，需要核实是否确实支持答案，不能只因页码不同就自动判错。这一小题集不能据此报告全库 Recall。

## 开发题与正式测试题

原问询题和江丰计算题都标为 development，用于发现问题并修改程序。复合题仍只计一道整题，另外观察是否遗漏子问题。题集里用于澄清的边界题不参加有答案题的检索准确率分母。

正式年报题集 annual_50_v1.jsonl 含 20 道开发题（茅台、格力各两年）和 30 道留出题（福耀两年）；两个分集单独保存在 annual_development_v1.jsonl、annual_test_v1.jsonl。问询题未混入这 50 题。题目、来源与核验统计见 annual_sample_manifest.json、annual_holdout_validation_v1.json。留出结果不得用于调整本轮规则；冻结后的工程变更需登记，不声称严格完全未变。

此处的 source_verified 表示由助手对照原 PDF 的文字层及页面图像核验；没有冒称已由用户人工审核。正式成绩发布前仍应复核标注与评分。

## 财务计算怎样接入

模型只识别需要计算的指标和期间。程序从公式白名单中选取已经实现的函数，使用核验过的事实和 Decimal 计算，再把结果及来源交给模型组织回答。不会让模型在每次提问时临时发明公式或执行其生成的代码。

financial_formula_reference.json 中的演示数值仍为假设值；新增 jiangfeng_2026h1_reference.json 使用用户提供 PDF 的原值，已做选定财务页的文字和图像核对。报告正文为 2026 年半年报，共 193 页，报告期为 2026H1，包含 2025H1 可比数；不是用户口述的 2022 年，也不是全年年报。收入、利润及现金流比较半年同期，资产负债按 2026-06-30 与 2025-12-31 分别记录，不年化。问询披露属性、公式演示和财务原值分开保存，已实际运行提取及五道计算开发题；最新逐题证据见 outputs/mock/acceptance/jiangfeng_workflow.json，不作为云端模型成绩。

PDF 第 56 页称未经审计，第 8 页称不追溯调整或重述以前年度数据；文件名的“更正后”只作为待进一步核对的版本标签。没有原版或更正公告，不能确定修改了哪些项目。第 62、67 页各自包含两张不同范围的报表，不能按整页给所有数值统一贴合并口径。

## 云端编码与生成的分工

当前已确定：意图识别、问题改写、拆题及答案/报告生成共用云端 DeepSeek-V4.1-Flash（API 型号 `deepseek-flash`）；文档和问题编码使用百炼 `text-embedding-v3`，1024 维 dense。DeepSeek 显式关闭思考并使用 JSON Object，再由程序校验；v3 经 DashScope 原生接口分别使用 document/query。向量库保存在本地，`BAAI/bge-reranker-v2-m3` 已本地接入并在 CPU 上运行，GPU 尚未验证。[DeepSeek 型号](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)、[百炼接口](https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api)

入库时全部待编码子块、查询时的问题发送至百炼；生成所需的原问、范围信息、选中证据与计算结果发送至 DeepSeek。原 PDF、解析结果和向量库保存在本地。两个客户端分别使用 DEEPSEEK_API_KEY、DASHSCOPE_API_KEY，百炼另配置实际 DASHSCOPE_EMBEDDING_URL。用户将在代码开发完成后自行填写环境文件，开发期间不要求提前提供 Key；本机流程已测，收费云端 API 联通与模型题目效果尚未实测，不把密钥写入题集或日志。

开发期间使用显式 mock 客户端验证流程、数据契约和错误处理，记录标明 mock；模拟向量、缓存、索引与正式数据隔离，不计算真实召回成绩、模型质量或费用。正式模式缺 Key 明确报配置未完成，不能偷偷返回模拟答案。用户配置后运行真实探针、重新编码 PDF 并用小题集做端到端验收，不能复用模拟向量库或把模拟结果当作 live 成绩。

本项目把工作分开：pdfplumber 提取 PDF，text-embedding-v3 将检索文本编码为向量，本地 BM25/向量库寻找相关材料，重排模型调整候选顺序，DeepSeek 使用证据回答，财务计算器完成确定性运算。文档用于编码和查询时提供证据，不是上传后自动重新训练模型。

正文 500/80 仍按固定版本 bge-m3 tokenizer 计数；只加载 CPU 文本计数文件，不加载 BGE 模型权重或生成向量。切分计数、v3 的 usage.total_tokens、DeepSeek 的 usage 分开保存。两家费用分开统计，文档首次入库、问题编码和重建用量分别报告。

向量返回按 text_index 对齐，缺项、错维度或失败批次不得发布索引；查询 API 失败不能计作无证据拒答。即使其他模型也是 1024 维，也不能混用向量；更换模型需独立建库。断网时可解析及浏览已有资料、运行已有核验事实计算，新编码、向量查询和生成依赖云端。

用户配置 Key 后，用真实开发题验证 v3 的证据命中与引用，不能把采用云端模型或通过模拟用例写成准确率已经提高。本地 bge-m3 推理仅留作后续可选对照，不是首版依赖。


## 参考事实与测试标签的边界

- `*_reference.json` 是与源 PDF SHA 绑定的财务字段核验参考，必须先从真实 PDF 抽出同一行列、期间、口径、单位和值，匹配后才升级为 verified；不会凭参考文件填补漏抽值。
- 带这些参考的数值结果属于“已核验事实输入轨道”，不能用来衡量完全自动财务抽取准确率。参考/标准答案不进入向量库，不作为待测问题的提示。
- `scripts/validate_experiments.py` 显式启用六份年报参考，只运行 mock。正式 50 题执行记录与开发 2 题各对照 smoke 分开记录；2 题对照不能包装成 50 题完整模型实验。
- `gold_complete=false` 表示标注未穷尽；报告标准证据覆盖率而不是完整 Recall。评分保留原始 TopK 位置，不用标准答案去重后将 K 外结果提进来。
- 引用语义支持、答案完整性等评分仍需独立复核；缺失评分为空值，不自动给满分。
